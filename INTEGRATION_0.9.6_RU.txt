ALEX BOARD 0.9.6 — ТЕХНИЧЕСКАЯ СХЕМА

ОБЫЧНОЕ ЗАВЕРШЁННОЕ ДЕЙСТВИЕ

1. Клиент формирует одну атомарную операцию.
2. Операция сначала записывается в IndexedDB pendingActions.
3. Только после завершения записи запускается отправка в Supabase.
4. Живой preview, рисование, движение, удаление и редактирование текста передаются через Ably.
5. После подтверждения pending-запись атомарно переносится в confirmedActions.
6. canvas.toJSON() после обычного действия не вызывается.

ВОССТАНОВЛЕНИЕ

Актуальный Canvas собирается так:

базовый snapshot
+ подтверждённые локальные операции после его revision
+ pending-операции
+ недостающие серверные операции

Подтверждённые локальные операции удаляются только после получения/создания более нового базового snapshot.
В локальном режиме журнал уплотняется при следующем открытии доски без чтения Canvas.

ПОЛНЫЙ SNAPSHOT

Полная сериализация Fabric Canvas остаётся только для редкой проверки целостности и аварийного сценария.
Серверный boards.snapshot в 0.9.6 продолжает обновляться внутри Supabase после принятой операции — это не блокирует главный поток браузера и сохраняет совместимость копирования/восстановления.

ТЕКСТ

Во время печати состояние текста показывается другим участникам временным Ably-событием object-live.
Одна долговечная операция записывается только при завершении редактирования текста.

КОПИРОВАНИЕ МЕЖДУ ДОСКАМИ

Выделение сохраняется в IndexedDB clipboard и переживает переход на другую доску.
При вставке всем объектам назначаются новые objectId.
Вся вставка является одной атомарной операцией, поэтому Undo удаляет её целиком, Redo восстанавливает целиком.
Изображения физически копируются в папку Storage целевой доски до вставки.

КОПИРОВАНИЕ ВСЕЙ ДОСКИ

Перед duplicate_board_v4 клиент идемпотентно подтверждает все pending-операции исходной доски.
После этого сервер копирует актуальный snapshot.
Изображения получают независимые файлы в папке новой доски; если перенос assets не завершился, незавершённая копия удаляется.

БОЛЬШИЕ ОПЕРАЦИИ

Если JSON операции превышает примерно 220 000 символов, клиент разбивает транспорт на части.
Части записываются через upload_board_import_chunk_v6.
commit_board_import_v6 собирает их в правильном порядке и один раз вызывает apply_board_action_v5.
Для остальных участников это остаётся одной серверной revision и одной Undo/Redo-транзакцией.
