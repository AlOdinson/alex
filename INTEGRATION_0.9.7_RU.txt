ALEX BOARD 0.9.7 — ТЕХНИЧЕСКАЯ СХЕМА

1. ЛОКАЛЬНОЕ ЗАВЕРШЁННОЕ ДЕЙСТВИЕ

Законченное действие
→ сериализуется только затронутый объект или группа
→ операция сначала записывается в IndexedDB pendingActions
→ локальный pendingCount увеличивается обычным счётчиком
→ полная очередь IndexedDB не читается
→ canvas.toJSON() не вызывается

2. ОТПРАВКА ОЧЕРЕДИ

Через короткое транспортное окно клиент открывает IndexedDB cursor по индексу:
   [boardId, createdAt]

Курсор получает не более:
   32 логических действий
   и примерно 700 KB данных

Эти действия передаются одним RPC apply_board_actions_batch_v7.
Каждое действие сохраняет собственные:
   actionId
   revision
   ops
   Undo/Redo-границу

Это транспортный пакет, а не объединение нескольких действий в одно.

3. ПОДТВЕРЖДЕНИЕ

Supabase возвращает отдельный результат для каждого actionId.
Все подтверждённые pending-записи переносятся в confirmedActions одной IndexedDB-транзакцией.
pendingCount уменьшается без повторного count()/getAll().
Ably-публикация подтверждения выполняется независимо и не задерживает следующий серверный пакет.

4. СЕРВЕРНЫЕ ОБЪЕКТЫ

Таблица board_objects хранит:
   board_id
   object_id
   object_json
   z_index — разреженный серверный order key
   updated_revision
   updated_at

Обычный новый штрих:
→ INSERT одной строки
→ object_count + 1
→ next_order_key + 1024

Обычное изменение существующего объекта:
→ UPDATE одной строки
→ порядок объекта сохраняется без count/rank-прохода по всей доске

Удаление:
→ DELETE одной строки
→ tombstone
→ object_count - 1

5. ПОРЯДОК СЛОЁВ И UNDO/REDO

Только явные layer-операции и restore получают reorder=true.
Все объекты одной reorder-группы временно исключаются из порядка, затем вставляются по конечным zIndex в возрастающем порядке.
Поэтому групповое перемещение слоёв, восстановление после Delete и Redo не применяются частично.

Обычный update получает preserveOrder=true в подтверждённом журнале. Это позволяет не вычислять полный порядковый номер объекта после каждого движения или изменения цвета.

6. CHECKPOINT

boards.snapshot остаётся базовым checkpoint, но не переписывается после каждого действия.
Новый checkpoint собирается из board_objects один раз на каждой 1000-й принятой ревизии.

Открытие доски:
   базовый snapshot
   + серверные операции после snapshot_revision
   + подтверждённые локальные операции после базы
   + pending-операции
   = актуальный Canvas

7. СОВМЕСТИМОСТЬ

apply_board_action_v4 и apply_board_action_v5 перенаправлены в v7, поэтому уже открытая старая вкладка не сможет снова включить перезапись полного snapshot.
Для старых клиентов upsert помечается как reorder=true, чтобы не ломать кнопки слоёв. После деплоя старые вкладки всё равно следует закрыть.

8. FABRIC

Во время pencil/line/shape/partial eraser:
   skipTargetFind=true

perPixelTargetFind включён только для object eraser.
enableRetinaScaling=false уменьшает количество пикселей, перерисовываемых на Retina-экране.
skipOffscreen=true не рисует объекты вне видимой области.
Удалённые и массовые операции применяются с объединённым render request.

9. КОПИРОВАНИЕ

Междосочный IndexedDB clipboard, новые objectId, независимое копирование изображений и staged bulk import из 0.9.6 сохранены.
Перед копированием всей доски pending-операции теперь также отправляются транспортными пакетами до 32 действий.
duplicate_board_v7 копирует строки board_objects напрямую и не зависит от возраста boards.snapshot.

10. ОТКЛОНЁННАЯ ОПЕРАЦИЯ В ПАКЕТЕ

Если сервер отклоняет одно логическое действие, транспортный пакет прекращается на первом отклонённом действии.
Подтверждённые действия до него сохраняются, само отклонённое действие удаляется из очереди и запускает восстановление,
а более поздние зависимые действия остаются pending и повторно накладываются на актуальное серверное состояние.
